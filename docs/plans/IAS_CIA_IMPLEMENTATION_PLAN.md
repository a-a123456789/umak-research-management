# IAS confidentiality, integrity and availability implementation plan

Prepared 4 November 2026 (Asia/Manila). Repository inspection and linked official guidance support this plan. Implementation steps and acceptance criteria below are **proposed**, except where explicitly identified as existing. No cloud or Android deployment was inspected. This plan supersedes the password/role recommendations in SECURITY_LIFECYCLE_SEARCH_QUEUE_PLAN.md for these IAS requirements; existing search/queue work stays separate.

## Decisions to correct before implementation

| Original requirement | Finding | Recommended decision |
| --- | --- | --- |
| Manuscripts are IP/confidential assets “under RA 10173” | RA 10173 protects personal information; it is not a blanket IP classification for every manuscript or dataset. | Classify unpublished manuscripts as institutional confidential material; apply DPA obligations to identifiable personal data, including applicable educational information. Document IP ownership, publication permission and retention separately with the institution. [1] |
| Student, Faculty, CRM isolation | Existing roles are only `student` and `staff`; all staff currently read every research record. A role alone cannot express assigned evaluators or coauthors. | Add `faculty`, keep existing role names internally, and use study membership and reviewer assignments in addition to permissions. CRM role must not imply access to every manuscript. |
| RLS `WHERE researcher_id = auth.uid() OR auth.jwt()->>'role'='crm_staff'` | Supabase helpers do not exist in this plain PostgreSQL app. This is a predicate, not complete policy DDL. The staff branch also violates assigned-officer scope. | Native PostgreSQL RLS with trusted transaction context, explicit command policies and membership/assignment checks. No Supabase migration needed. If later adopting Supabase, use server-controlled custom claims and account for JWT freshness. [2,3] |
| EncryptedSharedPreferences | **Deprecated in AndroidX security-crypto 1.1.0.** Android Keystore remains supported. | Use platform Keystore AES-256-GCM keys to encrypt persistent session secrets; store only ciphertext plus IV/tag in app-private storage. Plain SharedPreferences or DataStore alone does not encrypt secrets. Keep access tokens in memory where practical. [4,5] |
| Argon2id or bcrypt >=12 | Argon2id is preferred; bcrypt is a legacy fallback, not formally a deprecated API. Current implementation is synchronous scrypt with implicit defaults. | Switch to async Argon2id; preserve legacy verification and upgrade after successful login. Start calibration at m=19456 KiB, t=2, p=1 and strengthen as capacity permits. If rubric mandates bcrypt, use >=12 as requested, async calls and a documented 72-byte input limitation. [6] |
| HS256 JWTs | HS256 and JWTs are not deprecated. Current opaque tokens already support immediate logout and server-side role changes. | Retain opaque tokens for this single API. Propose 15-minute access lifetime and rotating, hashed refresh tokens only if persistent mobile sign-in is required. Use JWTs only for a documented multi-service need; pin algorithm, issuer, audience, expiry, key rotation and revocation strategy. |
| TLS 1.3, AES-256 | Valid goals, but application middleware cannot prove cloud storage, backups and all network hops satisfy them. | Prefer TLS 1.3; explicitly choose TLS-1.3-only if the requirement is strict and verify client/provider compatibility. Any TLS 1.2 allowance is a documented requirement change. Verify encryption separately for DB volumes, object storage, backups and mobile secrets. [7,8] |
| Token bucket + 5 failures/15 min | Token bucket burst/refill is not identical to a strict rolling window. Current express-rate-limit uses 10 login requests/minute, in process. | Shared atomic token buckets for request/upload capacity, plus a separate rolling failed-login counter. Neither an in-memory limiter nor resetting it per worker satisfies multi-instance enforcement. |
| Zod/ORM | Neither is a security requirement by itself. Parameterized `pg` is already appropriate. | Add maintained Zod schemas to centralize validation; retain parameterized `pg`. Validate bodies, params, query strings and metadata; schema validation does not validate document contents. |
| Append-only audit table | Runtime INSERT/SELECT-only grants exist; owner tampering and forged direct inserts remain possible. | Restrict inserts to a controlled writer, keep business changes and events atomic, then add external immutable checkpoints if administrator tampering is in scope. A local hash chain alone is insufficient. |
| Room offline cache | Room remains appropriate. No Android source exists here. | Cache public directories/instructions and template metadata in Room, template bytes in app-private files. Room alone does not encrypt a database. Do not cache private manuscripts under this requirement. [9] |

## Implementation order and concrete changes

1. **Baseline and contracts (1–2 developer-days estimate):** freeze route/role/visibility matrix and safe synthetic fixtures. Resolve publication fields, reviewer scope, temporary activation flow and decimal MB definition. Record current tests/dependency advisories. Add strict schemas and safe errors first; these make subsequent APIs consistent.
2. **Authorization and database boundary (3–5 days):** add faculty role, membership/assignment migrations, private-note separation, reusable permission gates and explicit serializers. Existing owner records become owner memberships; existing staff do not automatically become assigned evaluators. Backfill assignments through an explicit reviewed mapping. Deploy membership-aware API before enforcing policies, test migration on a disposable copy, then enable RLS in a controlled release.
3. **Credentials, audit and throttling (3–5 days):** async Argon2id, hash migration, optional activation/refresh tables, versioned audit writer, shared throttling. Establish audit before enabling new business mutations. Fault tests precede load tests.
4. **Private documents and cloud configuration (4–7 days):** upload intent → bounded upload to quarantine → verify/scan → finalize clean metadata → authorized download URL. Upload capabilities restricted to fresh object keys; finalize validates actual stored size/checksum/version and rejects reuse or overwrite. Enforce size at ingestion, not only afterward. For direct-to-cloud flows prove provider-enforced size bounds (S3 POST conditions where appropriate); otherwise use the bounded streaming API. Add orphan cleanup and scan retry/timeout limits. Enable bucket/ingress/DB encryption settings and verify in a synthetic cloud environment.
5. **Recovery and Android (backend 2–3 days; Android 4–7 days after its project exists):** automate encrypted/offsite backups and monitored drills; implement public-content endpoints, Room/file cache and Keystore session storage. Android work needs the actual app source/module and supported device/API-level matrix; it is a separate deliverable from this Express repository.
6. **Evidence and defense (1–2 days):** execute matrix, run selected benchmarks, record short demos, reconcile report claims and retain commit-bound evidence.

Estimates assume one developer familiar with the stack, synthetic data, available cloud credentials and no institutional approval delay. They are planning ranges, not delivery commitments. Suggested modules: `src/security/{permissions,context,validation,limiter}.js`, `src/storage/`, `src/audit/`, versioned `db/migrations/`, `test/ias-*.test.js`, `benchmarks/benchmark-ias.js`. These paths and commands are proposed until implemented.

### Native PostgreSQL RLS design

Resolve identity through the existing hashed session lookup; never accept identity/role context from request body, URL or unverified JWT. Check out ONE pool client, BEGIN, use parameterized `SELECT set_config('app.user_id',$1,true)`, and run all scoped queries through that client before COMMIT/ROLLBACK/release. Transaction-local context prevents pool leakage. Derive roles and assignments from server-controlled database records. Public metadata uses a dedicated, narrowly granted projection/role that cannot read manuscripts or internal notes. Do not accidentally make an owner-executed view bypass RLS; verify view ownership/security semantics explicitly.

Research policies conceptually allow SELECT to active members or assigned evaluators, INSERT to authorized researchers binding self as owner, UPDATE by field-specific permission plus membership/assignment, and DELETE only through approved workflows. RLS controls rows; separate table grants/views/functions control restricted columns and allowed transitions. Related membership/assignment policies must avoid recursive-policy loops. Index member/assignment lookup keys. Setup/admin credentials never enter runtime or mobile clients. Shared-role transaction context is defense against missing predicates; a fully compromised app/SQL execution capable of setting context remains a boundary limitation, so retain parameterized SQL and least privilege. [2]

### Password/session migration

Recognize the existing `salt:hex` scrypt format and a new Argon2id PHC string explicitly. Run legacy verification asynchronously with its **original** parameters; upgrading its cost before verification would break existing passwords. On successful login rehash and conditionally update against the old hash; malformed formats return a safe authentication failure. Keep SHA-256 for high-entropy bearer tokens; expensive password hashing is for human passwords. Await dummy-hash initialization and hash/verify operations. Bound concurrent expensive hashes to prevent memory exhaustion; bound the queue and reject overload with a safe status. Do not silently weaken parameters after a slow benchmark.

### Audit and recovery boundaries

Use a restricted transactional append function with fixed search_path, no PUBLIC execution and trusted field construction. Preserve `audit_logs` as read-only legacy evidence; do not fabricate historical old/new values. If chaining is selected, specify canonical bytes, version/domain separation, serialize concurrent append through a locked head, and preserve checkpoints outside the DB. Minimize old/new fields and IP retention because audit evidence can itself contain personal data. Establish institutional retention decisions before enabling indefinite logs or immutable backups.

Restore tests must verify policies/grants as well as rows. Existing ordered comparisons exclude large object storage, deletion replay and end-to-end TLS. Restore sequences must advance correctly; a smoke insert after restore checks this. Database and file snapshots need a documented common recovery point. Restore approved deletion events before reopening access; do not resurrect previously deleted subjects.

## Benchmark protocol and provisional budgets

Use synthetic inputs only. Record commit plus dirty-tree state/source hashes, Node/Postgres/OS/CPU/RAM, configuration, seed and fixture size. Keep raw samples, errors, timeouts, throughput and p50/p95/p99; never remove slow runs. Warm up 5 rounds, measure at least 30 per case, and randomize comparison order. HTTP capacity cases additionally run for at least 60 seconds at each concurrency (1, 4, 16), repeated 5 times with a low-volume probe for health/legitimate requests. Run memory/event-loop collection separately where instrumentation changes timing. Save to a new `benchmarks/results/ias-<run-id>/`; never overwrite algorithm evidence.

| Suite | Workload and comparison | Report / provisional gate |
| --- | --- | --- |
| Password calibration | Legacy sync scrypt baseline vs async Argon2id minimum and stronger candidates; isolated workers and same password distribution; known/unknown/wrong logins; concurrency 1/4/16 | Hash/verify latency, HTTP latency, RSS/peak memory, event-loop delay, rejected overload. Aim p95 login <=500ms at 4 clients on reference host, event-loop p95 <=50ms; provisional until measured. Different algorithms have different security properties: report cost, not “X times more secure.” |
| Authorization/RLS | 1k/10k/100k studies, memberships and assignments; indexed ownership/list/reviewer queries, equal authorized results; app-only baseline vs app+RLS in disposable schemas | Query plans, throughput, p95 and overhead. Aim <=20% p95 overhead with representative indexes, investigate rather than disabling RLS on failure. Benchmark must not use owner/BYPASSRLS. |
| Audit | Same authorized mutation with plain audit vs controlled writer, optional chain; concurrency 1/4/16; verifier 1k/10k/100k events | Throughput/latency overhead, lock wait/deadlocks, total verify time and detection coverage. Target mutation p95 <=250ms at 4 clients; no fabricated universal chain speedup. |
| Throttling/resource resilience | Deterministic refill tests first, then two API workers under legitimate and excess auth/upload traffic; inject shared-store outage | Allowed/rejected requests by identity/window, bucket accuracy, health latency, memory, safe outage behavior. Aim legitimate health p95 <=200ms at tested offered load; publish load and resources. |
| Upload/recovery | Valid 1/10/25MB files, chunking, bounded concurrent scans; recovery datasets at 1k/10k/100k studies plus measured object bytes | Upload/scan latency, RSS, queue depth, rejection count; recovery RPO/RTO and storage size. No universal upload time SLA before network/scanner measurement. Proposal: daily backups imply DB RPO up to 24h **only when last backup is verified and files align**; choose stricter RPO via PITR if needed. Trial RTO <=60min for largest synthetic case, not production promise. |

Correctness/security assertions block CI. Machine-dependent speed goals produce reviewable benchmark reports, not brittle cross-machine pass/fail claims. Offline cache is best shown with instrumented behavior and airplane mode; throughput benchmarking is secondary.

## Reproducible evidence and demo package

Safe baseline now (no DB, no .env, no cloud calls):

```sh
node --test test/ias-plan-baseline.test.js
```

This checks selected **existing API behaviors using a mocked DB**. It proves neither real database RLS nor cloud/mobile controls. Saved run output: `evidence/ias-plan/baseline.tap`. The runner deliberately verifies only current guarantees; missing controls remain gaps in the matrix.

Existing broader commands: `npm test`, `npm run demo:sqli`, `npm run backup:verify`. They require an explicitly disposable seeded synthetic DB/environment and some mutate/delete fixtures. Do not run them against a shared/live dataset. The plan did not rerun them. Existing `bench:features` measures search/EDF, not this security suite.

Proposed future command contract (not yet present): `test:ias:db`, `test:ias:storage`, `bench:ias`, `audit:verify`, plus Android connected instrumentation. Each suite must fail when its required environment is absent rather than silently passing a skipped cloud/Android control. Local emulation can test workflow, but actual-provider IAM/encryption/TLS evidence remains necessary.

Defense recording script after implementation (about 6–8 minutes total):

1. **Access, 90s:** owner opens synthetic study; unrelated student/faculty and unassigned staff denied; assigned staff allowed; canary internal note absent from researcher response. Show real DB query missing API filter still denied by RLS.
2. **Document, 90s:** anonymous object access denied, wrong MIME/oversize rejected, valid file quarantined then released, authorized temporary URL works, new request after short test expiry denied. Hide URL signatures and credentials from recording.
3. **Integrity, 90s:** staff feedback update produces old/new event; runtime edit/delete of audit denied; injected audit failure rolls business change back. If chaining is claimed, demonstrate external checkpoint mismatch on tamper.
4. **Availability, 90s:** sixth failed login blocked, second worker shares limit, controlled dependency failure has sanitized response. Show measured restore report and freshness alarm rather than waiting for a full restore in presentation.
5. **Android, 60s:** warm cache, airplane mode, process restart, directory/template opens with last-sync time; private study access still requires authorization; logout clears token storage.

Evidence folder per run: `manifest.json`, `test-results.tap`, `samples.csv`, `summary.json`, `report.md`, redacted provider config/protocol probes and demo recording. Record each control as implemented/tested/passed/failed/blocked separately. Do not label future acceptance criteria as executed results.
